## 1. 本轮结论与证据边界

现有工程已经接入官方 DSH，并有下载校验、官方管理适配、任务和作者资料等模块。但用户旅程仍存在实际阻断，不能认定为已经完成可交付的新手市场 MVP。应保留现有标准插件结构，优先补齐完整功能链，然后调整应用商店交互。

本轮由主控亲自操作 Windows 官方 Desktop；三名真实只读子智能体分别核查安装状态、目录与作者资料、客户端及交付完整性。没有修改市场业务代码、官方源码、组织仓库或用户真实 profile，没有提交、推送或发布。新增的本文件及 D 盘测试证据用于后续交接。

证据分类：

- **D：桌面复现**——本轮在官方软件中的实际点击与观察。
- **S：源码确认**——读取实际代码并核对调用关系；不等于桌面验收。
- **U：合成复现**——子智能体用官方字段形状和内存依赖复现；不等于真实安装。
- **未验证**——尚未执行，不计通过。

### 首次失败与重试缺陷必须分开

随后仅在专用测试 profile 新建 `.npmrc`，将 `store-dir` 指回原来的 `D:/.pnpm-store`。没有改全局设置。重新生成安装方案后，市场在调用官方安装器前被自己的 `plan/conflict` 阻断。因此没有证据称第二次安装已成功，也没有删掉历史任务来制造通过结果。

## 5. 安装路线：已有官方能力与待选取舍

官方管理器实际具有安装来源识别和 `installBundle`，来源类型包括 registry、路径、git 与 tarball。市场不需要再造 pnpm 安装器。但“一个 GitHub 仓库”不必然已经提供可直接运行的标准 bundle：源码可能还需要构建，缺少加载声明或缺少运行依赖。

| 方案 | 工作方式 | 优点 | 代价／边界 |
| --- | --- | --- | --- |
| A：已构建的发布包，推荐作为主路线 | 作者／团队发布固定版本 tgz，GitHub 与 Gitee 提供同摘要文件；市场选择来源、校验并把同一文件交官方管理器 | 新手只点安装；版本、来源、失败位置可复查 | 作者侧需先做标准打包与验证；顶层包摘要不自动覆盖所有传递依赖 |
| B：直接安装固定 git 提交 | 用官方支持的 git 来源，绑定确定提交 | 未单独发布制品的作者接入更直接 | 客户机可能需要构建、访问依赖；主分支变化及构建不确定性更大，不能冒充已校验 tgz |
| C：模型协助 | 读取脱敏错误、识别已知问题、建议换源／修包／重新核对；确认后通过允许的官方操作执行 | 对复杂错误解释更友好 | 官方 `plugin_manager` 的安装最终还是调用同一管理器；模型不能自动修复市场状态机，也不提供必然成功保证 |

官方模型工具依据：`packages/boot/plugin-manager/src/tools.ts:20`，公开动作包括 `list_plugins/list_bundles/set_plugin/set_bundle/install_bundle/remove_bundle`，受官方权限规则约束。该工具没有市场套餐确认、精确摘要及持久任务语义。若引入模型执行，必须复用市场队列与确认边界，不能与手点安装抢写，不能绕过硬兼容限制或把包 README 当授权。

待用户选择：本轮仅做好确定性安装；增加辅助诊断；或进一步提供经确认的受限执行。此文件不替用户决定。

| 错误 | 说明出了什么问题、已完成哪些、接下来能做什么；详情另展开 | 只展示日志容易实现，但不能达到新手友好目标 |
| 作者入口 | 次级入口：草稿列表→编辑预览→导出资料；投稿仍私下交接 | 在线账号平台更完整，按当前范围继续后置 |

视觉采用已读 `impeccable` 的 Operate/Read 原则：沿用宿主主题，统一字号留白、状态、焦点和按钮；可加入约 150–200ms 的短过渡。性能与动画必须分开验：先测大目录搜索、滚动、任务轮询和页面重开，再调整动效。没有实测前不写“60fps”或“已经丝滑”。

## 7. 内置插件、合作作者和推荐如何接入

建议继续分开维护运行代码与市场内容。以下为候选流程，并不代表已经完成收录。

1. **作者交付材料**：标准包或发布制品、原始技术声明、源码地址、版本、介绍、真实截图、使用／设置入口、许可证及必要授权说明。
2. **团队核查**：作者和包身份对应，制品可以由官方加载；旧 EAC 私桥依赖逐个查证，不能整目录搬过去就认定兼容。
3. **自动验证**：固定版本、计算摘要、检查公共格式、在官方测试环境安装；区分仅解析成功与实际运行通过。
4. **生成目录**：介绍、下载镜像、验证证据、插件技术资料独立关联；内容维护不改市场安装核心。
5. **推荐陈列**：市场私有展示记录承载精选位置、用途集合、排序和推荐理由。`builtin/recommended/external` 原公共语义不应被改成广告位语义。
6. **发布及撤回**：内容审核与发包权限分开；坏版本下架应停止新安装并告知受影响用户，不静默卸载现有内容。撤回／替代版本机制需与团队协商。
7. **未来基础包**：根据同一份经核验清单生成随包基础内容；完整离线版再验证所有依赖和许可证是否齐全。“随包目录”不等于“插件和依赖已在包内”。

组织方式的选项：同仓分目录最容易开始；独立内容仓更方便作者合作和无代码更新；从同一内容源额外生成完整离线版覆盖弱网，但维护成本最高。建议讨论“独立内容仓＋基础随包＋其余按需”，完整离线版后置。

已实时核对的团队分支：[beta-pack](https://github.com/DSH-EAC/DSH-Desktop-EAC/tree/44178ab1360dcb8221a666e782391a11f5716074)。其 Mojobox 样本中存在 `unpublished` 插件和仅 `Parsed` 的证据，不能直接标成当前官方 Desktop 已验证。公共 `Pack.requires` 是宿主／平台要求，不能改作组件依赖图。

## 8. 后续模型的候选工作顺序与分工

这是供讨论的实施骨架，用户选定交互和 AI 范围后，再编制正式逐文件计划及完整提示词。

| 顺序 | 负责人／独占区域 | 交付与进入下一步的条件 |
| --- | --- | --- |
| 0 | 主控：基线、公共 contracts、错误模型、计划身份／重试规则 | 重读官方接口与团队格式；将 F01–F21 转成可执行验收。给 worker 冻结输入，避免并行发明不同返回结构 |
| 1A | 安装 Worker：`adapters/dsh/**`、`core/**`、`persistence/**` 及相应测试 | 确认绑定、升级降级、keep、取消、重启、来源保护、错误保留及重试。每个修复都有失败复现和成功证据 |
| 1B | UI Worker：`client/**`、Client 测试、设计文档 | 先去遮挡和假成功，再按选定商城旅程调整。调用 impeccable，按实际接口联调，不用 mock 回执代替 Host |
| 1C | 内容 Worker：`catalog/**`、`delivery/**`、`authoring/**` 及相应测试 | 目录真实来源、失败一致性、公共格式与证据、草稿/媒体/ZIP往返；不自行改公共 Mojobox 协议 |
| 2 | 主控：集成、共享入口、生成和打包脚本、文档 | 干净目录可重建，最终 tgz 冻结并记摘要；不得用覆盖已安装文件代替装包 |
| 3 | QA：独占测试实例；Reviewer：只读 | QA 实际点击最终包，核对文件、状态、重启和恢复；Reviewer 查错误目标、未确认授权、假成功、证据和许可。一次一个实例写入者 |
| 4 | 主控 | 修复阻断并重跑受影响验收；发布仍按用户明确授权；未完成项如实保留 |

共同提示词应明确：全程中文；读取当前文件，不继承历史“已通过”；禁止改官方／组织仓／真实用户 profile；不得 commit/push/发布；不改别人的独占文件；新增依赖、公共契约和来源配置由主控统一；所有输出区分 D/S/U；模型辅助安装如获选，仍不得越过用户确认和官方限制。

QA 必须额外复验：从发现分类进入列表保留所选分类；A 方案切换 B；未验证未勾选；失败后修正环境重试；已装旧版更新及套餐降级；同版本保持；取消不倒退；待重启前置暂停；作者跨客户端 ZIP 往返及许可保留；刷新失败不显示成功；窄屏与键盘；市场自身被停用后的官方恢复入口。

本轮只运行了安装审查相关的四个已有纯测试文件（子智能体报告 19/19 通过），并做若干内存复现；没有重新执行完整检查或宣称完整验收通过。现有绿测恰好说明需要补充跨层、真实用户旅程测试。

## 9. 讨论顺序

第一轮已发给用户的两个问题：主页更接近精选应用商店、工具搜索市场，还是两者混合；安装失败后模型只诊断、确认后执行，还是暂不加入。

第二轮再讨论：安装确认是否自动生成清单；任务面板在宽窄布局下的形态；我的插件是否默认折叠系统组件；合作作者的资料和推荐审核责任。

完成这些选择后，正式计划必须附页面状态图、契约变更、文件所有权、子智能体提示词、每项验收和完成门槛。**当前没有用户的新选择，不把候选推荐写成已批准决定。**

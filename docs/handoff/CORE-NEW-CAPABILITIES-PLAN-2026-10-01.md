# Core 新增能力最小补齐计划：方案 A

日期：2026-10-01。版本：**方案 A v1.2（网络拉取调研复核版）**。状态：**P0 代码修补已完成；新增能力的真实官方宿主、首次空缓存发行链及真实网络验收尚未全部完成**。

本次升级依据接力线程“调研后端网络拉取不稳定的解决方案”（线程 `01a0f7ae-9c74-75c3-a830-75810cfdc06e`）。调研最初把组合二列为“覆盖复杂环境优先”；用户进一步指定“最轻量且有效”后，最终结论改为**组合一：现有 Core / Adapter 加单一 Node HTTP 路径**。后续答案覆盖前一轮的排序，本计划按最终结论执行；组合二、组合三只保留为有实测证据后的升级选项。

目标：沿用协作者现有设计，补齐 Agent Forge 来源、离线制品、Bundle 选择/取消、维护状态和更新策略的关键缺口，使新增能力能通过公开后端接口完成真实业务流程。后端稳定之后，再另行升级前端。

本计划采用后端接口方案 A：扩展现有 `MarketBackend`，由现有 DSH Adapter 转发。它与网络调研中的“组合一”以及旧拆包指南中“同仓双包方案 B”是三个不同层次的选择，不改变已经选定的双包结构。

**四条硬性要求：路径不依赖开发机；所有文件拉取必须有界、可校验、可恢复；首次空缓存安装链必须单独可用；官方 DSH 兼容通过能力探测和真实版本测试实现，不靠放宽版本号宣称成功。**

**轻量方案边界：**采用现有 Core / Adapter 加一条统一的 Node 网络传输路径（优先用目标 DSH Runtime 自带的 `fetch`，通过每请求 Undici dispatcher 接入代理；若目标 Runtime 无法提供已验证的 dispatcher，再由 Host 注入与其兼容的实现）。不得设置进程级全局代理或把网络切到多套客户端。本轮不强制 Motrix、aria2、libcurl、CDN、独立下载服务器或新的后台服务。只有在真实网络证据表明“可靠传输已正确接线但特定地区仍不可达”时，才重新评估分发层。市场自己的下载路径也不等于官方包管理器后续依赖的下载路径，两者须分开验收。

### 1.3 何谓“能正常用”

每个新增能力都必须具备：合法输入可通过公开 Backend 调用；校验/存储/恢复有真实行为；错误输入明确失败；执行复用既有计划/任务/锁；结果来自官方回执和库存核对；旧能力回归通过。

“稳定拉取”意味着：来源可达且内容合规时能完整取得；网络/磁盘失败时在有限时间内返回明确结果并保留可恢复状态。没有网络、来源删除、权限不足时不得无限等待或假成功。

类型声明、内部纯函数或内存缓存通过，不等于完整能力完成。能力不满足其适用条件时返回结构化 `unsupported`/`unavailable`/`blocked`；已派发且结果不明则保持 `unknown`，不能自动重放。

## 2. 沿用架构，补接线

```text
登记来源 / 用户授权的文件
        ↓
安全读取 → 身份与摘要核对 → 接受的目录 / 制品缓存
        ↓
Bundle 选择和依赖核对 → 冻结安装计划
        ↓
现有 TaskManager / 持久化 / profile 锁
        ↓
官方 DSH Adapter → 官方管理器 → 回执与库存复核
        ↓
维护状态 / 更新结果 / 任务结果
        ↓
MarketBackend → DSH Remote（前端之后消费）
```

责任：Core 负责目录投影、依赖/意图、计划和状态；Adapter 提供宿主身份、目录、网络/文件读取能力和官方动作；未来 Client 只展示、选择和确认。

只新增必要的注入接点，复用现有 `HostPort`、`ArtifactPort`、文件和锁接口。DSH 工厂仍是正式组装入口。补 `HostPort.remove` 及真实结果；移除业务运行时必须自己构造具体 DSH 对象的限制，保留旧工厂调用兼容。避免为了依赖注入重写整套 Runtime。

## 3. 跨机器、复杂目录和权限环境

### 3.1 路径合同

| 对象 | 路径来源与存储方式 |
| --- | --- |
| 随包目录和资源 | Adapter 使用 `import.meta.url` 相对当前安装包定位，读取原始字节后传 Core；不依赖工作目录 |
| profile / 数据根 | 官方宿主可信上下文提供；沿用 `<profile>/eac-market` 的逻辑位置，具体根由 Adapter 注入 |
| 缓存、临时文件、任务 | 从数据根推导；内部只保存相对路径、内容摘要或受控 handle |
| 用户导入文件 | Host 文件选择/授权产生 handle，或受控分块字节输入；Client 不自报任意绝对路径 |
| 目录内 package/index 文件 | 每个最终文件做 realpath、普通文件和授权根检查；阻止 junction/符号链接逃逸 |
| 历史官方 `file:` 引用 | 可在 Host 私有记录中保留实际绝对路径，但标为机器/环境绑定；对外不可序列化，换机不可原样恢复执行 |
| 测试/证据输出 | 由命令参数或环境变量指定，未提供时由测试 runner 建隔离临时目录；不写固定盘符和用户名 |

禁止生产代码、公共 DTO、目录和发行物依赖维护者的盘符、桌面、用户名、代理端口、源码 checkout 或 Motrix 安装位置。开发机工具约定不是产品运行依赖。

不能把“不能依赖本机环境”理解成禁止一切运行时绝对路径。官方安装器调用需要本机实际文件路径，但它必须来自可信 Host、运行时解析且只在 Host 内使用。

### 3.2 环境处理

1. 用平台路径 API 和文件 URL 转换处理路径；支持中文、空格、长路径、Windows/Unix 分隔符。ZIP 内路径使用固定 POSIX 相对格式，不调用 shell 拼接路径。
2. 启动/首次写入探测数据根和临时目录权限、可用空间；只读安装目录下仍应可读取包资源，并把写入放入获准数据根。
3. 临时文件与最终目标优先位于同一受控文件系统，用已验证的原子替换能力；跨盘不直接假设 rename 成功。ENOSPC、EACCES、锁占用、杀毒短暂占用应返回准确原因，受限重试。
4. 两个 profile 隔离缓存/任务归属；同 profile 多界面共用后台，写锁沿用既有执行占用规则。缓存引用修改与清理不能互相竞态。
5. 新意图/源配置记录采用独立版本化文件；沿用现有 schema3 任务迁移。新增冻结图若影响执行摘要，显式升级相应记录格式；旧程序不能忽略新执行字段继续执行。
6. 换机/迁移时可携带 `.eacpack` 与可重校验资料；安装计划、调用者挑战、官方回执和在途任务要重新绑定环境并重新确认。已安装 `file:` 依赖不承诺自动可搬迁。
7. 断电或磁盘写失败不能静默创建空状态覆盖坏记录；保留旧文件/备份，允许诊断读取，必要时暂停写入。

验收 PATH-01：不同用户、中文/空格路径、改变启动工作目录、只读安装目录、自定义数据根、跨盘临时目录、两个 profile、重启、换机模拟均有明确成功或受控失败结果；产物扫描无开发机路径/凭据。

## 4. 广泛兼容官方 DSH

### 4.1 三层兼容分别管理

- **准入层**：沿用官方对 DSH peers 的宿主语义。不要把 `workspace:*` 误变成开发机的旧 DSH 包，也不把 Cordis/其他依赖范围无证据放宽。
- **能力层**：读取实际官方服务和方法，检测 `read/inventory`、`install`、`setEnabled`、`remove`、`cancel`、`wait/reconcile`、持久化/锁和网络读取能力。
- **行为层**：按实测签名与回执转换，保留 `applied`、`restart-required`、`failed`、`cancelled`、`too-late`、`unknown`；异常字段不能被猜成成功。

Core API / Remote 版本协商继续保持主版本约束；新增兼容能力可升小版本，不兼容语义必须升级相应协议。支持一个新宿主，不等于可以忽略旧任务格式或调用者确认。

### 4.2 实施规则

1. 在现有 DSH Adapter 中集中做能力检查和少量差异映射，不把版本分支散落到业务代码，不按版本号盲目假定服务存在。
2. 已识别签名使用经过证据核实的参数，例如现有卸载的单包名调用。新官方返回结构先加适配和测试，再开放写能力。
3. 缺取消/回执查询能力时仍允许可证明安全的读取；涉及未完成写入的取消/恢复给出明确不可用/待核对结果，保留占用，不能用假空实现放行。
4. 宿主服务晚加载、重连、重启、能力变化后重新探测；同 profile 不创建第二份 Core 后台。
5. 缺官方原子写或锁时拒绝有副作用的执行，保留读取与诊断能力；不能普通 writeFile 冒充相同保证。
6. 保留当前 Node 24+ 基线；对 TLS/Abort/代理等可能随补丁变化的能力做探测，避免模块加载期硬引用不存在的功能使市场整体失效。
7. 未知新 DSH 版本可以尝试准入和读取，但写能力只有在接口结构与前置事实可验证时开放；无法识别的结果返回 unknown。不能声称兼容所有未来版本。

### 4.3 版本与平台矩阵

| 层级 | 需要的证据 |
| --- | --- |
| 官方 0.1.7-rc.2、0.2.0-rc.1 | 官方 peer gate、实际方法签名、隔离新装/启停/卸载/重启/取消测试；历史截图不能代替本次包 |
| 开工时核实的新官方稳定/候选发行 | 核实包身份与发布时间；用同一套探测和验收登记支持结果，不预写未来版本号 |
| 合成未知/缺能力服务 | 只验证安全降级、返回结构变化和零误写，不能标真实宿主兼容 |
| Windows / Linux / macOS | 路径、HTTP/TLS、原子文件和锁的自动化测试；只对实际运行过的平台登记支持 |
| 官方 Desktop | 本阶段官方真实宿主验收入口；AIO/Lite/自制壳不替代 |

验收 DSH-01：每个支持行有官方包版本/摘要、系统、能力表和真实动作结果；只通过 peer gate 的行单列“仅准入验证”。

## 5. 文件拉取稳定性：本轮必做

本章适用于 Agent Forge source/index/package、目录刷新、插件/Skill 制品、离线导入以及新增路径复用到的文件读取。作者/AI 既有能力只做受影响回归，不扩大产品范围。

### 5.0 网络方案比较与本轮决定

| 方案 | 优点 | 成本与边界 | 本轮决定 |
| --- | --- | --- | --- |
| **组合一：Node / Undici 单一路径** | 不要求用户另装下载器；代理、超时、取消、流式文件和缓存可集中管理；故障点少 | 仍须自行维护安全读取、续传与平台验收；不能凭一台电脑代表所有代理环境 | **采用**；先用它解决已复现的接线与传输问题 |
| 组合二：多种网络适配器 + 独立镜像/CDN | 可逐步覆盖更多代理和地区线路 | 每种适配都增加配置、证书、凭据、版本兼容与运维成本；增加镜像本身不能修正来源字段或状态错误 | 暂不引入；只有组合一实测未达目标且故障定位为特定线路时再选定具体扩展 |
| 组合三：aria2 / libcurl 等独立下载引擎 | 现成的部分大文件、队列和代理能力 | 增加多平台二进制、进程回收、升级、日志及安全边界；仍不能替代摘要/包身份校验 | 暂不引入；只有有 GB 级资源的实测需求并证明收益后复议 |

“轻量”指少维护一套常驻组件，**不删掉可靠性功能**。无论方案一还是后续可选扩展，都必须保留流式 `.part`、范围校验、有限重试、制品身份校验、取消清理和可见任务状态。Motrix 只可作为维护者获取外部文件的本机工具，不能成为市场用户运行依赖。

### 5.1 一个明确的读取边界

复用现有 `safeFetch`、HTTPS reader 与 `fetch` 注入点，先修配置和来源字段接线。所有目录、元数据、Skill/插件制品与导入包统一经过这一条 Node HTTP 读取边界；不得由 Agent Forge Reader、ArtifactCache、目录刷新各自再造客户端。优先使用目标 DSH Runtime 的 `globalThis.fetch`，代理通过兼容该 Runtime 的 Undici dispatcher **按请求**注入；禁止调用 `setGlobalDispatcher` 或修改整个进程的代理/TLS行为。只有实测证明 Node 内置 `fetch` 与 Host 可用 dispatcher 不兼容时，才在一个 Host transport 内锁定同版本的 Undici 实现，不增加第二套业务下载路径。

- Host 在初始化时从 DSH 明确提供的网络设置，或用户启用的标准 `HTTP_PROXY` / `HTTPS_PROXY` / `NO_PROXY` 环境配置生成私有网络配置快照。不得从目录条目、README、作者包或远程内容接收代理、CA、超时和重试设置。
- 第一阶段支持直连、HTTP/HTTPS 代理和已明确实现的 `NO_PROXY` 规则。规则覆盖精确主机/IP、域后缀/通配和可选端口；CIDR 目前**不得宣称支持**。Undici 官方文档列明的规则是主机匹配、`.domain` / `*.domain` 与可选端口，并未承诺 CIDR。当前测试样例虽写有 `10.0.0.0/8`，但只验证了域后缀跳过代理，必须增加 CIDR 正反断言，或删去该误导样例。
- 代理认证只保留在 Host 进程私有配置中，不能进入目录、任务、事件、日志或公开 DTO。dispatcher 要按代理配置复用并在 Host 关闭时释放；不能每个请求创建一个未关闭连接池，也不能把密码写入错误文本。
- SOCKS、PAC、Windows/macOS 系统自动代理和需要交互登录的企业网关，未经目标 DSH Runtime 的真实验证前返回明确的 `network-unsupported` 和配置指引。不能为“兼容”关闭证书验证、跳过主机名验证或绑定某台机器的本地代理端口。
- TLS 只接受目标 Runtime 已验证的系统信任链；自定义企业 CA 只有在 Host 能安全注入且保留主机名验证、并通过实际证书测试后才标为支持，否则明确失败。日志不得包含 Cookie、Authorization、代理口令、签名 URL 参数和个人路径。
- HTTPS、DNS/IP、重定向规则继续复用；每跳重新验证目标，禁止公网来源跳至私网/本机。跨 origin 时不得转发来源凭据。

**配置接线审计（新增 P0）：**逐段核对 `MarketService.Config.catalogSources`、`CatalogSourceRegistry`、Agent Forge `MarketCatalogSource`、`CatalogDelivery.sources`、`ArtifactAcquireRequest.delivery/sourceRef` 和 `ArtifactCache.download` 的字段映射。必须确认“来源地址、包名、版本、摘要、大小、来源类型、优先级”在每一段保持同一语义；文件已经下载但因内部字段误传而被后续校验拒绝，视为失败，必须在 NET/SRC 回归中固定复现并修复。

### 5.2 从开始到正文完成都受限

一个请求的取消信号和时间预算必须贯穿 DNS 检查、连接、TLS、响应头、正文读取、临时文件写入及摘要校验；不得在拿到 `Response` 后丢掉 signal。必须区分“速度慢但仍有数据”和“已停滞”：连接/响应头、正文连续空闲、单来源、整个制品任务、目录刷新各有独立上限。

**禁止统一 30 秒或 5 分钟包级总时限。建议默认参数按以下基准实现并由 Host 覆盖，之后依据代表性慢网测试调整；这些是工程预算，不是下载速度承诺：**

| 预算 | 起始建议 | 作用 |
| --- | ---: | --- |
| 元数据/连接与响应头 | 30 秒 | DNS、连接、TLS、取响应头；适用于小型元数据请求，制品正文另计 |
| 制品正文空闲 | 30 秒 | 连续没有新字节才判停，不限制仍在持续传输的慢下载 |
| 每来源基础预算 | 90 秒 | 覆盖 DNS、连接、请求建立和固定开销 |
| 最低吞吐基准 | 32 KiB/s | 已知文件按 `90 秒 + 文件字节数 ÷ 最低吞吐` 计算；未知长度按最大允许字节计算 |
| 每来源绝对上限 | 2 小时 | 防止单个来源永远占队列；Host 可调整但必须有硬上限 |
| 整个制品任务上限 | 动态总预算，绝对上限 4 小时 | 由冻结候选来源各自的大小预算及退避时间求和后封顶；不让 32 个来源把总等待无限放大 |
| 同一来源重试 | 默认额外 2 次 | 指数退避并尊重有界 `Retry-After`；网络错误分类后才重试，永久 404/身份错配不重试同源 |

**当前实现必须核对的旧配置陷阱（G1 阻断项）：**`ArtifactCache` 的旧 `timeoutMs` 目前可直接覆盖按文件大小计算的来源预算。必须确认正式 Host 没有把小型元数据请求的短超时传给大型制品；迁移为命名清楚的元数据、响应头、正文空闲、来源和任务预算。兼容旧配置时只允许映射到原本的窄范围，不能让 `timeoutMs=30s` 静默重新变成所有制品的总时限。当前每来源与整个任务都默认两小时也必须按上面的整体预算决策对齐，尤其要测试慢源接近超时后同摘要镜像是否仍有预算。
按此初始预算，200 MiB 文件约需 108 分钟，因此“五分钟全包时限”会误杀慢速但可用的下载。调研线程中的 9/19 分钟是按一次测速外推的估算，不是整包实测或所有用户的速度承诺；它证明固定五分钟可能不够，不可反向硬编码成 9/19 分钟默认值。单来源与整次任务上限不可共用同一个固定两小时值：一个来源若接近 108 分钟才超时，固定两小时总预算只剩约 12 分钟给同摘要备用源。

**整体预算仍有三种做法：**A 固定两小时总预算，等待上限清楚，但最大制品的慢源可能耗尽预算、令镜像没有机会；B 按冻结候选分别计算来源预算，累加有限退避后以四小时封顶，可给主源和备用源实际机会，代价是极端情况的后台任务最长；C 不设整次上限，覆盖更多候选但会让故障任务长期挂起，拒绝采用。推荐 B：每来源预算按上式计算、单来源封顶两小时；整次任务预算按冻结来源数、每源预算和重试退避求和，再由四小时总上限封顶。若超出总预算，停止并准确报告尚未尝试/未完成的候选，不能把镜像尚未尝试说成镜像不可用。未知大小仍同时受最大字节与任务总上限控制。Host 参数、最终配置和耗时/速率证据都要记录；不得把一次代理或宽带测量宣称成所有用户的保证。元数据刷新另设最大文档/记录/总字节和整次刷新预算，不与大型制品下载共用 30 秒。

- metadata 保留现有单文档体积上限，并增加总记录数、总字节和整次 refresh 时间预算，防止数千串行文件造成无限加载。
- 制品必须流式写 `.part` 并增量统计已接收字节；不先把整个制品放进内存。检查 Content-Length 与真实接收大小，缺/伪造长度也要限制。
- 第一版采用**单任务单来源、有限并发**，不做并行分片；同一摘要的并发请求共享/复用缓存，不能互相覆盖。重试只处理可恢复的 DNS/连接中断、429、5xx、响应中断等；单次失败按“同一来源有界重试→同摘要已登记镜像→结构化失败”收敛，不因读不到包就改版本或猜 `latest`。
- 断点续传列为本轮必做：保存 `.part` 元数据（目标摘要、冻结来源身份、已接收长度、ETag/Last-Modified 等验证材料）；续传请求必须核对 `206`、`Content-Range`、起点和来源身份。服务器返回完整 `200`、范围不匹配、文件版本材料变化或不支持 Range 时，丢弃残片并从头安全重取，不能把完整文件接在残片后面。
- 断点恢复完成后重新从文件计算完整摘要并执行 tgz 身份/结构校验；不能把残片阶段的摘要当成最终证明。首版不做多源并行分片和复杂下载引擎。
- 取消/超时关闭网络与文件流，停止重试/镜像切换；保留 `connecting/downloading/retrying/verifying/completed/failed/cancelled/unknown` 等可恢复状态。用户取消之后不得继续派发安装。

### 5.3 正文、制品与镜像校验

1. HTTP 200 先检查实际正文：HTML 登录页/限流页不能当 JSON 或 tgz；空正文、截断、损坏归档要有明确错误码。
2. 元数据核对 schema、source/index、revision、包名/版本/record 引用；安装制品核对大小、SHA256、tgz 包名/版本、归档安全和官方 bundle 声明。
3. 只在同一冻结包名、版本、摘要下换已登记镜像，不换旧版本、不现场从 registry 猜 latest；镜像候选与尝试原因可追踪。
4. 429/5xx/短暂超时可以在预算内退避，读取有上限的 Retry-After；永久 404 不反复重试。身份/摘要/目标错配和不安全路径不能当普通网络错误重试同一来源。
5. Gitee 签名内容重定向、GitHub Raw/经登记 API raw 内容、npm 精确 tarball 分别验证，不要求所有来源采用同一种重定向策略；仍不允许任意 redirect。
6. Agent Forge distributions 无法映射到受支持交付方式时，保留可浏览资料并返回缺失项，不编造摘要、作者或安装认证。

### 5.4 落盘、缓存与失败恢复

- `.part` 和最终文件按摘要/随机 ID 定位，只在受控根写入；完整校验后原子切换，安装器只能取得已校验文件。
- 下载、保留引用、导入物化和清理共享必要锁/协调；两个消费者拉同摘要不会互相覆盖引用或删除对方文件。
- 安装 profile 中仍被 `file:` 引用的缓存不能提前删；中断/取消按任务与安装引用回收，不以 UI 关闭作为清理条件。
- 旧缓存使用前核对摘要和身份；损坏缓存隔离并说明原因，不能无限重下损坏源或就地篡改同摘要内容。
- ENOSPC、EACCES、原子替换失败保留上一份完整文件和任务状态；失败不能报已下载/已安装。
- 对旧的绝对 localRef，恢复时重新验证根与环境，不因改了 dataRoot 就重放未知写入。

### 5.6 首次安装与官方后续依赖（新增）

市场自己的下载能力在市场首次安装前尚未运行，因此必须把以下链路单独验收：

```text
官方 DSH 添加市场
→ 市场 Adapter 制品可取得
→ Core 精确来源可取得或按发行合同由包管理器取得
→ 双包加载
→ 空缓存刷新目录
→ 插件/Skill 制品下载
→ 官方安装器处理其仍需要的依赖
→ 回执和库存核对
```

- 首次取得 Core 的来源不能指向“市场启动后才能提供”的自救地址；固定版本、来源、摘要和失败指导必须随发行合同提供。
- 下载到本地制品后，不得假设官方安装器不会继续访问网络；需要在有网、严格离线、依赖缺失三种场景分别记录真实结果。
- 严格离线时，只有依赖闭包完整且官方允许本地供应的包才可放行；官方仍需要远端依赖时提前返回 `offline-dependency-missing`/`offline-unsupported`。
- 这条链路由后端/发行验收负责，前端页面是否已经接入不影响其放行判定。

## 6. 新增能力逐项补齐

### 6.1 Agent Forge 来源

- 先提供可核实的 Agent Forge v2 公共 schema 基线和真实样例；不根据手写字段检查宣称完整标准兼容。
- 配置按 sourceId/目标登记，兼容原 `catalogSources` 配置；公开请求使用登记 ID，维护者才可增加 URL/本地授权根。
- source/index/package 名称、版本、latest、record revision 和 targets 全部交叉核对；类型和 distributions 不受支持时给出结构化原因。
- 缓存按来源与目标区分。整次来源读取/校验成功后才接受新 revision；同 revision 不允许内容悄悄变动。刷新失败后返回值、current() 和重启后的记录都保持 stale。
- 把原始记录投影到现有目录/交付/展示合同并接入 CatalogRepository，复用发行撤回/版本绑定/接受历史；未知 `_meta` 保存，不能把 checksum 当安全认证。
- 多来源相同身份采用确定的登记优先级；同包同版本不同摘要阻断，镜像不得覆盖权威来源撤回事实。不引入完整通用 registry solver。
- 在线 advisory 只在来源提供受支持索引时拉取；不存在时省略，不能拿空对象假装检查过。
- 保留 `discovery` 四区合同，无真实推荐/评分不生成；Skill 类型与 DSH 安装能力分别判断。

验收 SRC-01：在线、本地、离线源均能通过 Backend 产生同一目录合同；SRC-02：错包/错版/错 revision/错目标阻断；SRC-03：源失败保留旧目录；SRC-04：中文路径/junction；SRC-05：多源冲突、撤回和未来生效；SRC-06：无推荐/评分时不造数据。

### 6.2 本地 tgz 与 eacpack

- 新建本地安装导入会话，复用分块传输原理和安全工具；作者 transfer 当前 purpose/格式仅面向资料，不能把 tgz 塞成作者 ZIP。
- 会话绑定可信 callerId、环境、用途、总大小、摘要、TTL/配额；重复/乱序/错会话输入拒绝，输出不透明 importId，浏览器 DTO 不含绝对路径或 Buffer/Map。
- eacpack manifest、source/index、package targets 与当前 Agent 交叉核对；所有文件大小、摘要、引用与依赖必须自洽。扩展名和 ZIP 读取成功不表示安装成功。
- 对齐离线包与底层 ZIP 的大小/条目/展开上限；现有作者 ZIP 的上限不能无意限制宣称支持的大插件，且不能为离线包无限扩大内存。
- 物化文件接 ArtifactCache，tgz 复核后生成现有 plan/task；冻结来源、包名/版本/摘要及导入句柄，不在执行时重解当前目录。
- 严格离线模式禁止全部远端 fallback，包括官方包管理器可能需要的间接 npm 依赖。预检必须确认完整依赖闭包及官方合法本地供应方式。
- 第一版优先支持已验证自包含/随包依赖齐全的官方 bundle。缺间接依赖或官方没有可证明无网的供应方式时，安装前返回 `offline-dependency-missing`/`offline-unsupported`，不得后台联网补包，也不改包内 package.json/原始制品。
- 目录/Skill/MCP/general 资料可读取和核验；只有当前官方宿主具备相应安装入口、制品合法时才进入安装。原始 Skill 文件下载可通过受控 artifact handle/读流提供，不随意写官方目录，不伪装成 DSH bundle。

验收 OFF-01：本地 tgz/eacpack 合法导入→计划→任务→官方库存；OFF-02：错目标/摘要/身份拒绝；OFF-03：禁止网络时自包含 bundle 仍成功；OFF-04：缺间接依赖在派发前阻断；OFF-05：中断传输/重启/权限失败可核对；OFF-06：未知安装结果不重复派发。

### 6.3 Bundle 选择、依赖与取消

- 将 Agent Forge `type/bundleDetails.members[].memberId/memberType` 映射到既有选择图，不要求调用方手动拼内部节点。
- 分别检查成员包含循环和运行依赖循环、缺引用、重复身份/不同目标版本；对 conflicts/provides/replaces 做本轮支持的确定性核对。暂不能解析的语义明确阻断受影响项目，不静默忽略。
- 全成员保持可选；选择消费者时缺依赖则预检阻断，不能自动强选或下载。允许明确已安装且版本可核实的依赖满足条件。
- 在现有 PlanBundle 保存图 revision、选择来源（explicit/dependency）、来源 revision、目标摘要及保护事实，纳入摘要。冻结后不允许执行期间修改成员。
- 取消预览查询全局已安装依赖/其他任务/其他 Bundle/Explicit/完成/官方保护，不只看当前图；返回结构化保留原因。
- 普通取消阻止被依赖项；Force 二次确认绑定当前任务、图 revision、预览摘要、caller 和幂等键。只将当前任务中安全未完成项标为取消，不卸载已完成项。
- 选择计算的 `cancelled` 不作为官方回执；正在写的项继续保留执行占用，等待真实取消/终态/核对。too-late/unknown 原样返回。

验收 BND-01：成员/依赖循环与缺项；BND-02：选择/已安装依赖核对；BND-03：冻结后目录变化；BND-04：普通取消、Force 外部/并行/完成保护；BND-05：过期预览、重复确认、取消过晚、重启后依赖保留。

### 6.4 维护状态与意图恢复

- 以当前可信 Host 事实为准，活跃任务表示进行中，目标仅表示意图，终态历史仅解释过去。库存未知时保持 unknown；不能用固定的优先级忽略正在写入后的未知事实。
- 修复旧成功任务覆盖未安装/unknown、失败禁用显示 disabled、历史重启标记不随当前事实解除等问题。
- 增量持久化 Explicit/Dependency 意图：冻结预检不立即永久保留；用户明确选择与自动依赖分开；任务确认/结果、普通启停、卸载、取消、过期计划分别处理。
- 恢复时读任务和普通管理记录/新意图记录，不把所有成功项推断成 Explicit；对卸载及释放有可追溯的记录。不能从库存 provenance 猜用户意图。
- revision 覆盖实质库存、意图、依赖、活跃任务和待重启变化；新 API 同时输出结构化动作许可/原因。操作前仍在 Core 复核，不把旧 snapshot 当授权。
- 复用现有原子文件和锁，保持未知写入屏障；意图写失败不谎称成功，任务和意图中途断电可重建。

验收 STA-01：当前库存优先于历史；STA-02：明确启用/卸载后重启；STA-03：依赖不误标 explicit；STA-04：取消/过期预检不永久占用；STA-05：版本/启停/意图变化 revision 改变；STA-06：损坏记录不静默重置。

### 6.5 更新检查和策略

- `checkUpdates` 明确是比较已接受目录，还是先刷新指定来源；结果提供 checkedAt、sourceRevision、stale/刷新结果、当前版本、候选版本和原因。不能拿旧缓存声称公网最新。
- 选择合法、目标相容、未撤回且制品齐全的候选，不从无效最高版本推导“没有可用更新”。未知库存、本地改造包和硬阻断保留真实语义。
- 更新、手动或自动路径都复用现有冻结计划；默认保持当前启停选择。降级、卸载、权限扩大、脚本授权、重启/unknown 都要求对应确认或暂停。
- UpdatePolicy 通过新 API 保存，自动检查默认开、下载/安装默认关；一个 profile 一个可停止的有界定时检查，离线/关闭/失败不会自旋。
- 用户以后开启自动下载/安装时，只在显式记录的授权范围内创建冻结计划；无法证明授权足够就等待确认。自动检查不授予任何写权限。

验收 UPD-01：有更新/最新/未知/撤回/不兼容；UPD-02：检查无插件写入；UPD-03：策略保存恢复、调度退出；UPD-04：更新保留启停；UPD-05：自动选项开关、权限和重启暂停。

| 接口组 | 最小输入/输出 | 保护与归属 |
| --- | --- | --- |
| maintenanceStatus | 当前环境维护快照、revision、动作许可/阻断原因 | 只读；Core 计算，Adapter 原样转发 |
| checkUpdates | 登记 sourceId、可选 refresh；更新检查结果 | 比较只读，目录刷新会持久化，复用握手保护 |
| catalogSourceList / catalogRefresh | 登记来源安全信息、sourceId/importId、刷新结果 | 不向 Client 暴露本机路径；保留旧 sourceUrl 已登记校验兼容 |
| artifactImportBegin/Chunk/Finish/Dispose | 用途、大小、块序号、摘要→importId/预览 | 绑定 caller/environment/TTL/配额；不能伪造本机路径 |
| artifactGet / artifactRead | 只读信息或分块内容句柄 | 只向拥有者提供已核验文件，无通用文件读取能力 |
| bundleSelectionPreview | bundleId、revision、selectedIds→图/阻断/选择令牌 | 预览仅登记可过期选择；不下载安装 |
| planCreate | 原 selections 或受控选择/import 令牌→既有 PlanResult | Core 复核并冻结；trusted callerId，禁止混用身份 |
| taskCancelPreview / taskCancelConfirmed | 任务/目标→影响、挑战；确认→任务与保留项 | 普通取消兼容旧入口；Force 新确认、幂等和终态回执 |
| updatePolicyGet/Save | 设置及 expectedRevision→保存结果 | 修改设置有握手/调用者保护，不等同本次安装确认 |
| hello/capabilities | 实际可用能力、API/协议和宿主识别 | 未接线或未具备前提的能力不声明可用 |

每个 DTO 只有 JSON 安全字段；共享类型放 `contracts`。冻结方法名、字段、错误码、capability、版本要求、时限、取消、重入/重启行为和样例后再实现。明确 `PlanResult`/`TaskState` 与新增预览状态之间的区别。

接线路径：`Runtime → api.ts → dsh.ts → market/src/index.ts 的 Remote → 官方生成描述`。不直接导出 Node Reader 给浏览器，不让未来页面相对 import Core 源码。

保留旧方法与缺字段降级，新增能力按 API 小版本与实际 capability 协商；一旦改变旧写入语义则升级相应主版本。保持官方调用者身份来源、写前握手、一次确认仅绑定一个冻结意图。没有新 Client 的阶段，用后端测试 driver 通过公开工厂和官方 Remote 做验收。

## 9. 检查与证据要求

从仓库根执行，不含固定本机路径：

```powershell
pnpm install --frozen-lockfile
pnpm build
pnpm exec vitest run tests/catalog tests/delivery tests/core tests/core-api tests/adapter tests/persistence tests/host tests/protocol tests/integration
pnpm lint
pnpm test:pack
```

实际增加的 import/网络/兼容测试目录纳入上述阶段命令。定向检查通过后，最终候选再运行一次 `pnpm check`；只有新失败/改动才扩查，不反复全量运行。旧 Client API 联动只做构建/相关合同回归，不以视觉验收拖入当前范围。

官方路径通过运行参数或环境提供：

```powershell
node scripts/verify-official-compat.mjs --official-dsh-root $env:EAC_OFFICIAL_DSH_ROOT
```

执行前验证变量指向的是所测官方包，未提供时记录 not-run，不把跳过视为通过。新装/升级使用独立临时 profile 和空包缓存，读真实官方管理器结果。抓包/测试 driver 可证明严格离线未产生 HTTP/DNS 外连；不能只关闭 Core 的 fetch 就宣称官方 npm 安装完全无网。

证据按 U（纯函数）、I（市场真实存储/锁+假宿主）、N（真实网络文件）、D（官方宿主）、P（最终包）区分。每项记录：提交、包版本/摘要、官方版本/摘要、平台、环境类型、方法、实际结果、pass/fail/blocked/not-run、未验证项。

本次已复现的故障必须变为“修正行为”的回归用例：历史成功覆盖当前未安装/unknown、失败禁用、Explicit 重启丢失、包名/版本错配、junction 越界、离线 targetAgent 错配、Bundle 成员循环、stale/current 不一致、revision 未覆盖管理变化；再加上来源配置字段误传导致“已下载但后续拒绝”、慢速大包被固定总时限误杀、Range 续传拼接错误、代理认证泄漏、首次空缓存 Core/Adapter 取得失败和官方后续依赖缺失。原探针 reproduced=true 是问题证据，不是正确行为期待。

完整完成门槛：新增能力全部有公开 Backend 闭环；PATH/NET/SRC/OFF/BND/STA/UPD 必需场景通过；未支持输入明确阻断；旧流程回归；正式目标平台和官方版本有真实证据。未完成真实宿主或外网验收就写 partial，不以测试绿宣布交付。

网络实现依据：Node.js 官方 Fetch 文档说明 Node 内置 `fetch` 接受 Undici 兼容的每请求 `dispatcher`，并可读取 `process.versions.undici`；Undici 官方文档说明 `EnvHttpProxyAgent` 可按配置的 `HTTP_PROXY` / `HTTPS_PROXY` / `NO_PROXY` 选路、可作为请求级 dispatcher 使用，且其 NO_PROXY 有明确匹配边界；RFC 9110 明确服务器可以忽略 `Range`，且 `If-Range` 验证不匹配时可能返回完整表示，因此客户端必须验证 206/Content-Range/验证器，不能盲目拼接。以上资料说明协议实现方式，不替代 DSH 实际运行验收。

| 决策 | 采用方式 | 另一方式的代价 |
| --- | --- | --- |
| 公开能力 | 已选方案 A：扩展 MarketBackend，分阶段兑现 capability | 只留内部函数需要后续再次接线，不能完成这次目标 |
| 运行路径 | Host 注入根/handle + 包相对资源 | 硬编码机器目录导致换机、升级、只读安装失败 |
| DSH 兼容 | 能力探测 + 少量已验证映射 + 真实矩阵 | 仅放宽版本不能证明实际 API/回执可用 |
| 文件传输 | 单一 Node transport（优先 fetch/Undici）+ Host 网络配置；流式 `.part`、进度、重试、Range 恢复和最终校验 | 新造下载框架或引入专业引擎维护面大；只提高超时而不落盘恢复仍不稳定 |
| 断点处理 | `.part` 元数据 + Range/206/Content-Range 校验；不支持 Range 时安全从头重取；完成后重新摘要和身份校验 | 多源并行分片/aria2 增加平台、进程和安全成本，本轮不做 |
| 离线 | 官方合法本地流程，完整依赖预检 | 偷偷联网或重写安装器不符合离线和官方边界 |
| 持久化 | 复用现有原子文件/锁，增量意图记录 | 新数据库/全量状态重写超出最小补齐范围 |

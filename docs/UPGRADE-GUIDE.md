# 团队维护与升级指南

当前双包底座先读 [Core / Adapter 指南](CORE-ADAPTER-GUIDE.md)。业务模块现位于 packages/market-core/src；桌面入口/Client/Remote适配仍在 packages/market/src。公开接口、协议协商和两包发行必须一起验收。下文历史要求仍有效，旧路径按此映射。

本文件保留团队维护约定，并补入2026-09-28的真实实施入口。功能验收以当批测试与桌面证据为准，文件存在本身不算通过。

## mvp.1 升级先读

- 升级前停止旧市场执行器，保留当前 profile 下 `eac-market` 数据。新任务摘要 schema3 兼容读取旧schema1/2，首次写前留旧摘要备份；旧程序不能理解schema3，不能直接原地降回旧版本继续写入。
- 旧未发起计划缺冻结来源/连接绑定，需要重新预检；旧回执未知的任务不会自动重装。不能删除记录来解除写入阻断。只有核实旧官方写入停止、共享状态明确后才可继续。
- v2市场索引同时支持官方bundle元数据及真实dsh-std；旧v1缓存可读。接受过较新发布序号后，旧镜像/v1不能覆盖已知撤回。清空接受历史会失去该保护依据；离线无法得知新的撤回。
- 同包同版字节变化不是一个新镜像。新增源先在维护者 `catalogSources` 配置登记；用户作者图文和任意URL不授予目录信任。
- 作者接收与样例命令见 [作者指南](contributing/AUTHOR-ONBOARDING.md)、[目录维护](contributing/CATALOG-CONTENT.md) 和 [实际CLI](../scripts/catalog/README.md)。正式发布资料和许可仍须团队提供，测试模板不可原样进入生产。
- 扩展API和生命周期见 [扩展指南](../packages/market/src/client/extensions/README.md)，独立包见 [示例](../examples/market-extension/README.md)。三个主导航不变；核心安装确认不允许替换。
- 真实包仍由官方安装页安装。先在隔离profile验证升级、启停、重启、作者资料、最终包SHA与源码对应，再按授权发布；不要从本地单元测试推断其他系统或正式合作插件已支持。

## 1. 先找到该改哪一层

| 要做的事 | 主要改动位置 | 不应顺手改的内容 |
|---|---|---|
| 改插件介绍/截图/教程 | Presentation、媒体、Index引用 | 技术Manifest、制品摘要、历史Evidence |
| 收录新插件/新版本 | 真实Catalog记录、制品、Delivery、对应介绍 | 官方加载规则和整个UI代码 |
| 添加/调整套餐 | Pack与Lock、相应展示内容 | 已安装用户的版本与启停状态 |
| 调整套餐执行依赖 | 市场私有PackExecution、绑定Lock摘要与测试 | 公共Pack.requires的宿主能力语义 |
| 增加GitHub/Gitee镜像 | Delivery与来源策略测试 | 同版本的预期digest、公共Lock schema |
| 官方DSH升级 | adapters/dsh、打包/生成工具、能力与集成测试 | 大面积修改纯core和内容资料 |
| 内部API升级 | contracts及正反fixtures、Host/Client兼容握手 | 静默重解释旧字段 |
| 改视觉 | client、DESIGN、主题/键盘/窄屏测试 | 安装计划算法或profile存储格式 |
| 改持久化格式 | persistence迁移、schema版本、旧数据fixture | 把坏数据清空来躲过兼容问题 |
| 引入线上作者服务 | 新publication adapter/服务、身份与审核协议 | 作者本地草稿/导出格式的既有意义 |
| 后续Star能力 | 独立授权与支持流程 | 插件安装成功判定、强制登录或静默代点 |

## 2. 新维护者上手顺序

1. 读用户README、PRODUCT、docs/index、architecture、protocol，理解当前能力和未验项目。
2. 看当前分支/未提交改动，再看目标DSH版本、protocol版本、目录revision和最终包摘要。
3. 从package.json获取实际check/build/pack/test命令，在专用环境跑最小包检查。
4. 从需求→某模块→接口→调用方→真实UI结果依次追踪；不能只确认函数名和文件存在。
5. 确定修改范围和owner；多人只改各自文件。协议、包锁、构建、生成物源头由主控统一。
6. 完成最低必要测试后更新证据与文档；提交/推送/发布按会话授权，发布正文中文。

## 3. 收录插件与升级版本

**仅改介绍**：固定对应插件身份→检查许可证/截图来源→编辑Presentation→净化与schema验证→更新内容摘要/Index→预览→review。不用重算技术Manifest digest，也不用重新宣称功能测试通过。

**新插件**：

1. 确认真实作者、仓库、许可证和公开制品；没有制品标不可安装，不能猜下载URL。
2. 解包核对name/version及官方`package.json.dsh`加载声明。社区dsh-std元数据有则按它声明的版本验证，无则不得捏造facet。
3. 如果是Mojobox对象，按其自身流程新增/更新Manifest；保持原字节摘要与Lock引用一致。官方不接受的包形态不能靠市场手写用户层代码强装。
4. 为精确制品建立Delivery。备用镜像必须读真实文件比较摘要；不同构建字节即不同制品，需要修发布，不直接加入同一镜像组。
5. 写易懂用途、需求、使用入口、设置说明、必要账号/大资源提示。不能写作者未验证的“零配置可用”。
6. 在隔离官方DSH测安装/启停/卸载/需重启与关键功能；签发新Evidence，明确环境，不覆盖旧证据。
7. 通过目录schema和关系检查，再按审查/发布授权更新线上索引。Catalog更新不自动改变用户插件。

**新版本**：先新增独立版本记录、制品与证据；保留旧版历史用于说明/诊断。引导用户手动更新，重新展示影响。不要仅替换同一URL下的二进制让旧digest失效。

## 4. 维护套餐与未来全家桶

套餐由Pack表达“选了哪些功能”，Lock锁“具体装哪份”。版本调整、必需/可选组件、依赖与摘要必须成对验证。不要把未知的组件间依赖当没有依赖。

公共Pack不含组件依赖图；另维护PackExecution，绑定Lock原字节摘要，给出complete/partial/unknown和installed/active前置。更新Lock后旧执行记录不可直接沿用。MVP只有已核实完整图的套餐可一键执行；前置插件更新需重启时，其active依赖项暂停，待用户重启、核对、继续。维护者不能凭“包已在磁盘”跳过运行版本验证。

用户已同意套餐可在确认后调整已有版本；计划应明示升级与降级并保留既有启停意图。目录维护者不能用修改套餐绕过这次确认。

未来基础全家桶建议采用独立bootstrap（首次初始化入口）消费同一Catalog/Lock与安装服务，而非把自动预装写进市场每次apply。bootstrap必须记录用户已完成/跳过的选择，不反复安装用户卸载的插件。基础随包可用与完整离线包分别验收：离线包还需要传递依赖、运行平台、产物格式和许可的真实闭包，不能只把几个tgz放ZIP就宣称断网全可用。

旧EAC插件逐一对照官方标准接口迁移，不能把旧 `window.dshDesktop` 方法和壳专属路径带进市场。市场本身只管理已适配的产物。

## 5. 新来源与下载策略

先确认域名/路径、HTTPS、鉴权要求、重定向、限速、同制品摘要；首版以公开可读制品为主。来源不可达是网络事实，不直接推断插件不存在。

新增provider实现ArtifactPort并测：请求超时、中断续后重下、摘要不符、磁盘满、取消、重定向安全、缓存引用、URL失效。默认有界重试，不悄悄调全局npm registry/系统代理。

若将来支持私有源，先单独设计凭据最小权限、系统安全存储与日志脱敏，不能把token嵌入公共Catalog或分享的诊断。

若引入签名，单独定义密钥来源、轮换和撤回策略；哈希比对不是签名，旧记录不能自动标为“已验签”。

## 6. 官方 DSH 升级

1. 同时记录旧/新版本、源码/归档身份、公开接口diff。不要因目录名叫master就捏造commit。
2. 审查package metadata、slots/main/sidebar、Remote/Typert、pluginManager结果、profileContext、原子文件与Desktop进程包管理链。
3. 最小golden插件在新版重打包并安装，核验所有schema引用/exports和Host/Client分别加载。
4. 只在adapter中吸收兼容差异；需要新的行为时先修contract和fixture，不能在UI到处判断版本。
5. 跑单项/套餐/更新/启停/卸载/取消/恢复/数据隔离/作者工具/官方UI的受影响用例。
6. 实际通过后才扩大`peerDependencies`或目录验证范围；未通过的平台保留未验证/不支持标记。
7. 若新版接口实质冲突，保留旧版可用产物并说明支持矩阵，不能改官方源码来伪装标准兼容。

Client可能缓存旧JS，而Host已经升级。协议主版本冲突必须禁写并提示刷新/重启；兼容新增字段也需默认值与协商，不靠“同一个npm包”假设两端同时升级。

## 7. 公共协议与内部Schema升级

公共Mojobox/dsh-std升级按原仓规则：固定新revision，比较schema、正反fixture和生产样本，记录迁移影响；必要时请对应维护者评审。不要为了市场字段方便就改公共规则。

内部Schema遵循：可选增量→小版本；删除/重解释→主版本；旧数据通过明确迁移，迁移前保留旧文件。每次至少一个旧样本、合法新样本、非法新样本和中途失败测试。

任务状态不要回收旧枚举用于新意义。已完成任务关联的Catalog/计划摘要不可因当前目录刷新而失去解释能力；保留需要的快照或不可变计划原文。

## 8. 作者在线服务：下一版入口

本版只有本地编辑/导出。下版可选：

| 路线 | 优点 | 代价 |
|---|---|---|
| Git仓库PR投稿 | 历史/审核透明，团队工具成熟 | 新手作者仍需引导；身份与媒体协作不够直观 |
| 独立作者后台 | 投稿/认领/审核体验统一 | 需要长期托管、账号、安全、审核和备份 |
| 客户端编辑+服务提交 | 复用本版编辑器，界面一致 | 仍需可靠后端，不能把签名密钥/管理token放客户端 |

未来由用户与团队选择。PublicationPort只传可验证资料与身份凭证，不授予任意技术目录修改权限。作者认领应验证仓库/发布权；图文的更新权与可执行制品的发布权分开。审核后自动发布也必须保留撤回、审计、滥用处理和恢复入口。

导出的AuthorExport v1应该仍能导入新平台，不迫使作者重写介绍。服务器下线时本地草稿/导出仍可用。

## 9. Star 与GitHub支持功能：单独决策、单独授权

MVP不实现也不申请相关权限。未来需要重新核对GitHub规则并确认界面文案、OAuth权限和撤销机制。遵守已经讨论过的方向：用户主动选择支持、设置控制提醒、安装不强制Star或登录。

首版不能先放“支持作者”按钮背后偷偷Star；未来设置勾选也要明确影响的仓库与动作范围。用户拒绝/撤销不影响下载安装。不要把默认同意埋在通用条款中。

## 10. 发布和回退范围

发布前固定源码、包摘要、构建依赖和测试环境；将最终tgz与验收版本一一对应。修改一行代码后旧tgz/截图不是新版本证明。

市场自身升级先在隔离官方Desktop验证；不自动卸载正在运行的自己。保留上一份可用市场插件包和升级指南，官方允许时用官方管理手动调整版本。**插件版本回退不自动等于恢复用户配置/数据**，遇到存储迁移要说明是否兼容，不能承诺任意降级。

已安装第三方插件的包管理修复由官方规则决定，本市场不承诺完整文件/配置回滚。后续若引入救援能力应独立方案/权限/故障验收，避免与守岸人或Launcher同时抢写。

## 11. 每次升级的简短检查表

- [ ] 已读取当前工作树和上游变化，未覆盖他人工作。
- [ ] 事实、推断、建议、未验证分开写；使用了正确的官方版本和协议来源。
- [ ] 对应contract、调用方、UI、失败/取消/清理、注释和文档一起更新。
- [ ] 新制品摘要来自真实文件；旧Evidence未被改写。
- [ ] 同profile并发、用户disabled、本地fork、缓存引用没有退步。
- [ ] 实际跑了所需测试，真实Desktop缺项没有冒充通过。
- [ ] 无账号秘密、真实profile、测试默认数据和无许可素材进入产物。
- [ ] 对外动作按当前会话授权；未授权只准备可审查草稿。
## 本批更新

正式下载入口及源码维护总目录已写入根README。版本0.1.0-mvp.4包含二级皮肤中心及公开目录；目录从旧本机seq2保持同sourceId升级到公开seq3，不能清空接受历史。CatalogRepository构造器第4参数为随包原始字节，宿主正式调用必须提供，防止不同换行/缩进造成同修订不同摘要。

新增条目分类只消费包内dsh.skin公约，未知资料使用listings只读表。皮肤服务是可选Cordis依赖，安装/移除后应动态更新、释放监听。参考docs/contributing/DISTRIBUTION.md及src/client/skin-service.ts。

默认测试不依赖本机D盘源码：外部固定协议设置EAC_PROTOCOL_READONLY_REPO，官方槽位专项设置DSH_SOURCE_DIR，7-Zip独立归档校验设置EAC_7ZIP。正常pnpm check应能从新目录运行；不要把这些可选外部测试的跳过记成通过。
